Stage A–F structured discovery using the PROPOSE → evidence → jury model. The agent structures the inquiry; you provide domain knowledge at every gate. Governed by PRD-2.1, PRD-2.5, BUS-7.1 (all NON-NEGOTIABLE), ENG-11.1, ENG-13.1.

👥 Who uses this: Product Owner ✅ Discovery Sponsor ✅ Technical Coach ✅ Senior Architect ✅ DC-12 · Persona Routing

DC-08 🎯 When to Use — Product Discovery

✅ Use Product Discovery when:

  • ✅ You have a product hypothesis that needs validation before building
  • ✅ Leadership needs evidence before committing engineering resources
  • ✅ The problem definition is unclear or disputed among stakeholders

❌ Do NOT use if:

  • ❌ You already have validated requirements — go straight to Greenfield
  • ❌ You're trying to justify a decision already made — Discovery is not a rubber stamp
🎲

DC-11 · Discovery is the most human-intensive workflow. The agent structures the inquiry; you provide the domain knowledge at every gate. Stage B (Field Study) requires real interviews — the agent cannot conduct them. Stage D (Validation) requires your judgment on what "enough evidence" means for your context. The PROPOSE → evidence → jury model is essential here.

⚡ Workflow chain
Trigger: "Run Product Discovery Stage A for [product idea — e.g. loyalty miles calculator]" Preceded by: None required — can run standalone Followed by: Greenfield Development (if discovery validates the hypothesis)

🔒 DC-10 Stage Gate Evidence — Stage A

stage-a-problem.html

Problem statement + hypothesis clarity, mode/tier declared, stakeholder approval recorded

"Is the hypothesis testable and falsifiable?"

  • Hypothesis is phrased as a solution, not a problem → Reframe: "Users struggle to X" not "We should build Y"

Market research, competitive analysis (PRD-2.4), user interviews (PRD-3.1), JTBD framing (PRD-2.3). ⚠️ Real interviews required — the agent structures the guide and synthesises results, but cannot conduct interviews. Gate: ≥3 validated user insights; competitive landscape documented.

DC-09 📋 Prompt Library — Stage B: Field Study
🖥 CLI — gh copilot ask
gh copilot ask "Run Product Discovery Stage B Field Study: design an interview guide for [problem statement]. Suggest 5 interview questions that test the hypothesis. Remind me: I must conduct real interviews — the agent will structure the analysis."
💬 IDE Chat
Design an interview guide that tests this hypothesis. Structure the field study for Stage B.

🔒 DC-10 Stage Gate Evidence — Stage B

stage-b-field-study.html

Interview guide + synthesis template; ≥3 validated user insights; competitive landscape summary

"Did real interviews happen? Is the synthesis honest and unbiased?"

  • Interviews conducted or synthesised entirely by the agent — not valid evidence → Conduct real interviews; return raw notes for agent synthesis
  • All interviewees agree 100% — possible confirmation bias in participant selection → Seek disconfirming participants; revisit recruitment criteria

Repository ingestion, codebase assessment, domain model extraction, tech debt inventory (ENG-3.1). Analyse the Stage B field study data — produce supporting and contradicting evidence table. Gate: evidence report in hangar-ai-specs/; no unreviewed critical findings.

DC-09 📋 Prompt Library — Stage C: Evidence
🖥 CLI — gh copilot ask
gh copilot ask "Run Product Discovery Stage C Evidence: analyse the field study data from Stage B. Identify supporting and contradicting evidence. Produce a quantitative evidence summary."
💬 IDE Chat
Analyse the Stage B interview data. Identify supporting and contradicting evidence for the hypothesis.

🔒 DC-10 Stage Gate Evidence — Stage C

stage-c-evidence.html

Evidence table: supporting vs contradicting, quantitative summary, critical findings

"Is there enough evidence to proceed to validation?"

  • Only supporting evidence listed — no contradicting evidence column → Confirm disconfirming evidence was actively sought; add it

Stakeholder review, assumption mapping (PRD-2.2), problem validation (PRD-2.1), blocker resolution. Design a minimum viable test (MVT) with explicit Go/No-Go criteria. Gate: all blockers resolved; DVFT matrix complete.

DC-09 📋 Prompt Library — Stage D: Validation
🖥 CLI — gh copilot ask
gh copilot ask "Run Product Discovery Stage D Validation: design a minimum viable test (MVT) to validate the hypothesis using the Stage C evidence. Define Go/No-Go criteria."
💬 IDE Chat
Design a minimum viable test for this hypothesis. Define Go/No-Go criteria from the Stage C evidence.

🔒 DC-10 Stage Gate Evidence — Stage D

stage-d-validation.html

MVT design + Go/No-Go criteria + DVFT matrix; all blockers resolved

"Are the Go/No-Go criteria measurable and agreed by stakeholders?"

  • Go criteria are vague — e.g. "users like it" → Demand specific, measurable metrics: "≥70% task completion in ≤2 attempts"

Define success metrics, baselines, and PMF targets (PRD-6.1). Align to constitutional PRD laws. Confirm measurability. Render + human browser review. Gate: metrics spec in hangar-ai-specs/specs/.

🖥 CLI — gh copilot ask
gh copilot ask "Run Product Discovery Stage E Metrics: define success metrics for [product] based on the validated hypothesis. Align to constitutional PRD laws (PRD-1.x). Produce a metrics baseline document."
💬 IDE Chat
Define success metrics from the validated discovery. Align to PRD laws.

🔒 DC-10 Stage Gate Evidence — Stage E

stage-e-metrics.html

Metrics table + PRD law citations + measurability confirmation + PMF targets

"Are these metrics measurable and aligned to the problem we discovered?"

  • Only vanity metrics listed — e.g. page views, DAU without outcome framing → Demand outcome metrics: retention, task success rate, NPS delta

Now/Next/Later roadmap (PRD-4.2). Outcome framing (PRD-4.1). Vertical slices defined. Each roadmap item must reference the problem statement and be scoped to a constitutional Greenfield proposal. Gate: roadmap approved; implementation hangar-ai-specs/changes/[impl-id]/ scaffolded; PDF generated (ENG-13.3).

🔒 DC-10 Stage Gate Evidence — Stage F

stage-f-roadmap.html

"Does this roadmap represent the discovery outcomes honestly, without scope creep?"

  • Roadmap includes features not discovered in Stages A–E → Remove scope-creep items; they belong in a separate discovery
