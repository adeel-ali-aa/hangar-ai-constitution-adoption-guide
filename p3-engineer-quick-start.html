⚡ Run Your First Governed Task

DC-04
Step 1
Adopt the constitution
The constitution must be in your repo before any governed task. Use the adoption workflow, then paste the prompt into your AI agent.
→ Adoption Workflow
Adopt the Hangar AI Constitution into this repo. Clone from github.com/AAInternal/hangar-ai-constitution.git to ./../ and follow the adoption workflow.
Step 2
Start your first proposal
Paste the prompt below into your AI agent. Describe your ticket in one sentence and scope it to one class, endpoint, or service.
Read the Hangar AI Constitution. I want to work on [describe your ticket/feature in 1 sentence]. Create a constitutional proposal for this change. Scope it to [one class/endpoint/service] only. Include the applicable law IDs.
Step 3
Review the proposal
Read it carefully before typing APPROVE. Check:
  • Does the scope match your ticket?
  • Are the test requirements clear?
  • Is the batch size right — could it be smaller?
Step 4
Approve, implement, and archive
Type APPROVE to let the agent run IMPLEMENT. Review the changes — do they follow the proposal? Are there side effects outside scope? Then type ARCHIVE to close the loop and create your governance trail.
🤖 What is the Agent Doing? (DC-03)

🤖 What is the Agent Doing? DC-03

The agent works in governed phases. You stay in control at every gate.

📋
1 · PROPOSE
Agent reads your ticket description and the constitution. It proposes what to change, which tests to write, which laws apply. This is a governance document — not code yet. No files are modified at this stage.
🧑‍💻
Your turn
You read the proposal. Check scope. Reduce if needed: "Scope this to one class only." When you are satisfied, type APPROVE. The agent will not proceed without your explicit approval.
⚙️
2 · IMPLEMENT
Agent writes the code + tests (TDD: failing tests first, then implementation). Runs the SonarQube gate. Commits with a reference to the proposal ID. You review: does the code match the proposal? Any unexpected side effects?
🗂️
3 · ARCHIVE
Proposal moves to hangar-ai-specs/archive/. Your PR now has a governed history. This is the constitutional trail — every decision traceable to a law citation. Reviewers and auditors can follow the full reasoning chain.
🎲 DC-11 · Non-Deterministic Workflows

The agent's output varies between runs. This is by design — not a bug.

  • Two identical prompts may produce different proposals. Both can be constitutionally valid.
  • Your APPROVE decision is the gate. It is never automatic.
  • If the output isn't right, scope it down and re-propose — the constitution supports iteration.
  • Use the phase gate evidence to verify the agent stayed within your approved scope.
🧭 Human Agency & Adaptive Scope (DC-07)

🧭 Human Agency & Adaptive Scope DC-07

You own the scope. You own the approval. You own the architecture.

1
Your ticket, your scope
The agent will propose the full scope it can see. You are NOT required to accept it all. Scope it to one class, one endpoint, one service. Small changes done well beat large ones done poorly.
2
Tests come before code ENG-4.1 ⛔
The constitution requires TDD. The agent should write failing tests first, then make them pass. If it writes implementation first, OBJECT. You have the authority — and the obligation — to enforce this.
3
The SonarQube gate only checks NEW code
Don't worry about pre-existing issues in the codebase. The gate only requires that your new code doesn't add new violations. You are not responsible for the entire repo's historical debt in one PR.
4
You control iteration
Didn't get everything in one session? That's fine. Close the proposal, commit what you have, open a new proposal for the next piece. The constitution is designed for iteration — not big-bang delivery.
5
ARCHIVE closes the loop
Don't skip the archive step. It creates the auditable governance trail your team can review during code review and audits. Without it, the PR has code but no constitutional history.
📋 Full Engineer Workflow (DC-01)

The Hangar AI Constitution must be adopted into your repository before any governed task can begin. Without it, the agent has no laws to reference, no workflows to follow, and no archive location to write to.

→ Go to Adoption Workflow

Choose the workflow that matches your task:

  • Legacy Rescue — Modifying or refactoring existing code with a debt burden
  • Greenfield — Building a net-new feature from scratch
  • Avatar — Complex or cross-cutting work where the agent needs deep context about your system

→ Workflows Hub

Describe in one sentence what you are changing. The agent creates a constitutional proposal including the specific laws that apply, the test requirements, and the proposed scope.

Review: does the scope match your ticket? Is it appropriately sized? Are the applicable law IDs correct? Reduce the scope if it feels too large — you can always open a follow-up proposal.

The agent must write failing tests before writing any implementation. ENG-4.1 ⛔ is a hard gate — no exceptions.

Verify: tests exist and are failing before implementation begins. Cover the change fully. The target metric for your changeset:

new_coverage ≥ 90% on changeset

If the agent writes implementation first, stop it and require the TDD sequence. You have the authority to enforce this gate.

Once tests are written and failing, the agent writes implementation to make them pass. Review the result:

  • Does it follow the proposal exactly?
  • Are there side effects outside the agreed scope?
  • Does it introduce new dependencies not in the proposal?

If you see scope creep, raise it before archiving. You can re-scope and re-implement without losing the constitutional trail.

The agent runs the constitutional SonarQube gate. Read sonarqube-delta.md to understand the results. The gate checks:

  • No new bugs introduced by your changeset
  • No new vulnerabilities introduced by your changeset
  • New coverage on your changeset meets the threshold

Remember: the gate only evaluates new code. Pre-existing issues in the codebase do not block your PR.

→ Read Phase Gate Evidence Guide

The agent archives the proposal to hangar-ai-specs/archive/. Your PR description references the proposal ID. Every decision in the code is traceable to a specific law citation in the constitutional trail.

Code reviewers and auditors can follow the full reasoning chain from ticket description → proposal → implementation → archived evidence. This is what makes the PR constitutionally governed.

▼ Coaching Notes for Engineers (DC-06 · Socratic)
▼ Coaching Notes for Engineers (expand for Socratic prompts)
Prompt 1 — Scope & Risk
"Before you type APPROVE — what would happen if you approved this full proposal and it took 3x longer than expected? What scope change would make it feel safe?"
Prompt 2 — TDD Gate (ENG-4.1 ⛔)
"The agent wrote implementation before tests. What does ENG-4.1 say about that? What would you do?"
Prompt 3 — Mutation Score
"Your mutation score came back at 45%. What does that mean about your tests? What would a surviving mutant look like in your code?"
Prompt 4 — Architecture Communication
"How would you explain to a senior architect why you scoped the proposal to one package instead of three?"
